# Contributing

Corrections are the point. A wrong source, a misgraded claim, a broken figure, or a confusing sentence is a useful contribution.

## Before you start

- Read [docs/METHODOLOGY.md](docs/METHODOLOGY.md) and [docs/LIMITATIONS.md](docs/LIMITATIONS.md).
- For a claim correction, open a **Claim correction** issue first if the change is large or contested.
- Do not add private, paywalled, or unverifiable material. The repo ships only public sources and reproducible analysis.

## Setup

```bash
make install
make all
make preview
python3 -m http.server 8000
# open http://localhost:8000/preview.html
```

`make all` runs the offline pipeline, rebuilds the preview, runs the paper guard, and executes the test suite.

## Changing a claim

1. Edit the relevant entry in [`data/claims.yaml`](data/claims.yaml).
2. Keep the status, evidence grade, source IDs, and note internally consistent.
3. If you add a source, add it to the source register and capture a public URL or a frozen snapshot.
4. Run `make all`. Fix any schema, statistics, or paper-check failure.
5. Explain the change in the pull request: what was wrong, what evidence you used, and what else might be affected.

Do not silently round a conflict. If two sources disagree, keep both values and mark the claim `conflicting`.

## Changing analysis or figures

- Preserve the offline default. Network access belongs in `make fetch`, not `make all`.
- Do not commit refreshed benchmarks unless the hardware and method are documented. Benchmarks are hardware-dependent; the committed `results/bench.json` is the version of record.
- Add or update a test when you change a calculation, a generated output, or the preview contract.

## Preview changes

- `preview.html` is the source of truth; `index.html` is generated by `make preview`.
- No external JavaScript, fonts, trackers, or API keys. The page must work from a local file and from GitHub Pages.
- Keep the page usable on a 390 px viewport and with keyboard-only navigation.
- Do not invent a live URL, testimonial, customer, or market claim.

## Pull requests

- Keep the change focused.
- Run `make all` before opening the PR.
- Describe the user-visible effect and any trade-off.
- Link the issue or source that justifies the change.

## Style

- Plain English first; jargon second.
- Prefer short sentences and concrete numbers.
- Match the existing Python and HTML style.
- No emojis in code or generated files unless the surrounding file already uses them.
